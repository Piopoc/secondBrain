# Analysis of WA - 12

## Overview
The folder `WA - 12` contains a series of educational materials focused on **Web Security**. The content covers the fundamentals of cybersecurity, the CIA triad, and provides detailed analyses of three critical web vulnerabilities: SQL Injection (SQLi), Cross-Site Scripting (XSS), and Cross-Site Request Forgery (CSRF), along with their respective mitigation strategies.

## Detailed File Analysis

### image0.jpg
This file serves as a transition from HTML basics to web security.
- **HTML Links**: Discusses opening links in new tabs (`target="_blank"`) and the ability in HTML5 to wrap block elements within `<a>` tags.
- **Introduction to Web Security**: 
    - References the **OWASP Top Ten** as the primary source for critical web security risks.
    - Defines the **CIA Triad**:
        - **Confidentiality**: Ensuring data privacy.
        - **Integrity**: Ensuring data is not altered.
        - **Availability**: Ensuring service availability.
    - **Motivations for Attacks**: Lists economic gain (ransomware), industrial/political espionage, hacktivism, and personal challenge.

### image1.jpg
Focuses on **SQL Injection (SQLi)**.
- **Definition**: An attack where malicious SQL code is inserted into input fields to deceive the database server into executing unauthorized queries.
- **Examples**: 
    - Authentication bypass using comments (`admin' --`) to ignore password checks.
    - Using tautologies (`' OR '1'='1`) to retrieve all users from a table.
- **Impact**: Authentication bypass, unauthorized data reading/modification/deletion, and potentially executing system commands.
- **Defense**: The primary defense is the use of **Prepared Statements (Parameterized Queries)**. This separates the code channel (SQL structure) from the data channel (user input), ensuring input is treated as literal data and not executable code.

### image2.jpg
Focuses on **Cross-Site Scripting (XSS)**.
- **Definition**: Injecting malicious JavaScript into a web page that is then executed in the victim's browser.
- **Types of XSS**:
    1. **Stored XSS (Persistent)**: The payload is saved on the server (e.g., in a database) and served to every user who visits the page.
        - *Case Study*: The **Samy worm (MySpace, 2006)**, which spread virally by adding the attacker as a friend and copying the script to the victim's profile.
    2. **Reflected XSS (Non-persistent)**: The payload is "reflected" off the server, typically via a malicious URL parameter (e.g., in search results).
    3. **DOM-based XSS**: The vulnerability exists entirely on the client side, exploiting the Document Object Model (DOM) without necessarily involving the server.

### image3.jpg
Covers **XSS Defenses** and introduces **CSRF**.
- **XSS Defenses**:
    - **Output Encoding**: Transforming special characters (e.g., `<` to `&lt;`) to prevent browser interpretation as HTML.
    - **HTML Sanitization**: Using libraries like DOMPurify to remove dangerous tags.
    - **Avoiding Raw HTML**: Displaying user input as plain text.
    - **Modern Frameworks**: React, Angular, and Vue provide automatic output escaping.
    - **Content Security Policy (CSP)**: An HTTP header that restricts which scripts can be executed.
- **Introduction to CSRF**: Defines Cross-Site Request Forgery as an attack that induces an authenticated user to perform unwanted actions on a site.

### image4.jpg
Focuses on **Cross-Site Request Forgery (CSRF)** and provides a final synthesis.
- **Mechanism**: Exploits the fact that browsers automatically send session cookies with requests. An attacker creates a malicious page (e.g., `evil.com`) that sends a forged request (e.g., a fund transfer) to a target site (e.g., `bank.com`) while the user is authenticated.
- **Defense**: The modern solution is the **`SameSite` cookie attribute**:
    - `Strict`: Cookie is never sent in cross-site requests.
    - `Lax`: Cookie is sent only for top-level GET navigations.
    - `None`: Cookie is always sent (requires `Secure` attribute).
- **Comparison Summary**:
    | Attack | Vector | Target | Primary Defense |
    | :--- | :--- | :--- | :--- |
    | **SQL Injection** | DB Input | Database | Prepared Statements |
    | **XSS (Stored)** | DB $\rightarrow$ Browser | Victim's Browser | Output encoding, CSP |
    | **XSS (Reflected)** | URL $\rightarrow$ Browser | Victim's Browser | Output encoding |
    | **CSRF** | Third-party site $\rightarrow$ Server | Authenticated Session | Cookie `SameSite` |

## Synthesis
The materials present a comprehensive progression of web vulnerabilities. While **SQL Injection** targets the server-side data layer, **XSS** and **CSRF** target the client-side trust relationship between the browser and the server. The common thread is the danger of trusting user-supplied input. The synthesis emphasizes a "defense-in-depth" approach: using parameterized queries for databases, strict output encoding and CSP for the frontend, and secure cookie attributes to protect session integrity.
